## 決まっていること（ユーザーの決定。変えない）

| 項目 | 決定 |
|---|---|
| 対象の加工 | 板金。**形状解析（STEP・DXF）と金額の計算は今のまま**。画面をそれに合わせる |
| AI が数値を出す範囲 | 今のシステムと同じ。Web での単価調査、AI による工数・単価の推定、マスタ登録の提案は **作らない** |
| 画面の技術 | React（TypeScript）。**Streamlit は外す**（`app.py` とその画面テストを削除し、Docker・README・資料からも外す） |
| ログイン | **今回は作らない**。API の合言葉（`API_TOKEN`）は今のまま。あとでログインと権限を足せる作りにしておく |
| データベース | PostgreSQL を入れる（docker-compose に含める）。テストは PostgreSQL なしでも動く形でよい（SQLite など） |
| 置き場所 | クラウドか社内サーバーかは未定。どちらにも置ける作り（Docker）にする |
| 見積書を発行できる条件 | **金額に必要な項目がすべて入力されていること。** 入力されていれば、不確かな値（図面の読み取りが要確認、形状解析が概算）でも確定として扱い、発行できる。未入力が1つでもあれば発行できない |
| 表面処理「なし」・特急「なし」 | 入力済みとして扱う |
| マスターにない材料・加工・表面処理 | 似たものに寄せない（今のまま）。**ユーザーがその見積のための単価を入力する**。材料は「kg単価」と「密度」、加工と表面処理は「1か所（1個）あたりの単価」。入力がなければ発行できない。入力した値はその見積だけに使い、マスターには自動で登録しない |
| 形状解析が解析不可のとき | 図面PDFや入力から分かる項目は入れておき、金額に必要で埋まらない項目（**板厚・展開面積・切断長・穴数・曲げ数**）をユーザーが入力する。埋まるまで発行できない。内訳に「手入力」などの表示は出さない |
| 希望納期 | 見積の項目として追加する。記録・見積書への表示・進捗の警告に使う。**金額には影響させない**（特急は今までどおり人が指定する） |
| 類似図面・類似実績の条件 | **材料が同じ、曲げ数の差が1以内、穴数の差が2以内**。差が小さい順に並べる。図面一覧の「似た図面を探す」と、見積画面の「類似実績」を同じ条件に統一する（今の `src/similar_quotes.py` の条件はこれに置き換える）。曲げ数・穴数が分からない図面（形状ファイルがない）は対象外 |
| 図面の登録 | AI の仕分けは作らない。1件の図面は「図面PDF＋形状ファイル（STEP／DXF）」の組（片方だけでもよい）。図番・品名・顧客は人が入力する。図面PDFがあれば、今の読み取り器で図番・改訂・材質などを下書きとして入れる。改訂は新しい版を手で登録し、版の一覧を残す |
| 書類・ナレッジ検索 | キーワード検索だけ。対象は文字データのある PDF・Excel と、登録済みの図面・見積 |
| 帳票 | 見積書に加え、受注した見積から同じ金額で納品書・請求書を作る。請求書には適格請求書の登録番号と税率別の合計を入れる。テンプレートは表示項目の切り替えまで |
| 取引先 | 協力会社の単価・納期・評価は記録と表示だけ。見積の計算には使わない |
| 担当者 | ログインがないので、設定で登録した担当者の一覧から選ぶ（案件・見積の担当、振り返りの担当者別集計に使う） |
| 見積ロジックの画面 | 計算式の表示だけ。画面で式や費目を変える機能は作らない |

## 最終ゴール

モックの21画面のうち下の17画面を、React の画面として使えるようにする。図面を登録し、登録した図面から見積を作り、案件として進捗を追い、見積書・納品書・請求書を発行し、受注・失注を振り返るまでが、1つの画面のまとまりでつながること。データはデータベースに保管され、複数人が同時に使っても壊れないこと。

## 満たすこと

- **処理を2か所に書かない**：画面は API だけを呼ぶ。金額・判定を画面側で計算し直さない。画面・API・帳票で金額が一致する
- **解析と金額計算を変えない**：`src/sheetmetal_*.py`・`src/dxf_analyzer.py`・`src/pdf_reader.py`・`src/quote_engine.py` の結果は変えない。変える必要があるのは、見積の条件の扱い（未登録の単価の入力、解析不可のときの形状の値の入力、発行できる条件、希望納期）と類似の条件だけ。入力した単価・形状の値でも、金額は `QuoteEngine` がルールで計算する
- **発行の可否は API が決める**：未入力の項目の一覧を API が返し、未入力があれば帳票の発行を API が拒否する（画面のボタンを無効にするだけにしない）
- **データベース**：図面・版・案件・見積・帳票の発行記録・取引先・書類・担当者・ステータス・分類・属性項目・マスター・自社情報を保管する。スキーマの変更は移行の仕組み（マイグレーション）で管理する。今の `data/past_quotes/history.csv` と `data/*.csv` は初期データとして取り込む。**評価ハーネスと既存のテストは、今までどおり `data/` の CSV を使う**（画面でのマスター編集が評価の結果を変えないこと）
- **ファイル**：図面PDF・形状ファイル・帳票PDF・書類は、今の `FileStore` の形で保管し、置き場所を環境変数で変えられる
- **同時利用**：2人が同じ案件・見積を同時に更新しても、黙って上書きしない（後から保存した側に知らせる）
- **あとでログインを足せる**：だれが操作したかを入れる欄（今は担当者の選択）と、API の守りを1か所にまとめておく
- **LLM**：新しく LLM を使う機能は作らない。図面PDFの読み取りは今の読み取り器を呼ぶだけ。テストは API を呼ばない（偽のクライアント）
- **Docker**：`docker compose up` で、データベース・API・画面が起動する。Windows / PowerShell での起動手順を README に書く

## Claude API の呼び出しとテストの量

- **Claude API の実際の呼び出しは、実装が終わるまでの合計で最大200回。** 超えそうになったら呼び出しをやめ、状況を報告する。呼び出すのは、図面PDFの読み取りを画面から実際に動かして確かめるときだけ（少数の図面で足りる）
- 同じ図面は応答キャッシュ（`.claude_cache/`、`CLAUDE_CACHE_MODE=record`）で再利用する。テストと通しの操作のテストは API を呼ばない（偽のクライアント）
- **図面PDFの評価（`scripts/evaluate_pdf.py`）は実行しない。** 300枚で数百回の呼び出しになるため。`src/pdf_reader.py`・`src/pdf_terms.py` を変えないことで、読み取りの精度が変わらないことを保証する
- **過度なテストは不要。** テストは、金額・発行できる条件・類似の条件・データの保存といった、間違うと困るところに絞る。画面ごとの細かい表示のテストや、同じことを確かめる重複したテストは書かない。通しの操作のテストは主な流れ1本でよい

## 受入条件

| 項目 | 条件 |
|---|---|
| API の呼び出し | Claude API の実際の呼び出しが合計200回以内。最後に回数を報告する |
| 画面 | 上の17画面と、担当者の設定・過去見積のCSV取り込みが動く。作らないと決めたもの（Web単価調査、AI推定、AIの仕分け、AIに質問、差分比較、部品構成、ログイン）が画面に残っていない |

| 類似 | 材料が同じ・曲げ数の差1以内・穴数の差2以内のものだけが、差の小さい順に出る（テスト）。図面一覧と見積結果で同じ結果になる |
| データ | API を再起動してもデータが残る。過去見積の種データと CSV マスターが初期データとして入る |

| 回帰 | `python -m pytest -q` がすべてパスし（Streamlit の画面テストは削除してよい。金額と発行できる条件にかかわる内容だけ、API のテストで確かめる）、STEP・DXF の評価（`--gate`）が合格のまま。図面PDFの評価は実行しない（読み取り器のコードを変えていないことを示す） |
| 資料 | README、`CLAUDE.md`、`docs/`（03 画面設計書・04 操作マニュアルを新しい画面に合わせ、02 設計書にデータベースを追加）、`analysis/api_design.md` を直し、PDF を作り直す |

## 制約

- 正解データとホールドアウトに関する `CLAUDE.md` の決まりはそのまま
- 金額を LLM に計算させない。LLM の出力をそのまま数値に使わない
- 公開リポジトリ：秘密情報・実在の会社名を入れない（例のデータは架空）。プッシュ前に `python scripts/check_secrets.py --history`
