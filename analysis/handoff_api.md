# 引き継ぎ：本番に向けたサーバー（API）の切り出し

## 背景と全体の進め方

今の画面は Streamlit のデモ（`app.py`）で、画面と処理が1つのファイルに混ざっている。本番で使えるようにするため、次の3段階で進める。

1. **（今回）サーバー部分を切り出す**：解析・見積・見積書・類似見積などの機能を FastAPI の API として出す。Streamlit の画面も同じ処理を呼ぶ形にし、デモは動き続ける
2. React（Next.js、TypeScript）で本番の画面を作る
3. ログイン・複数人での利用・データベースを入れて、Streamlit を置き換える

本番の置き方（多くの工場が使うクラウドのサービスか、工場ごとの社内サーバーか）は **まだ決まっていない**。どちらにも置ける作りにする。

## 最終ゴール

今の機能をすべて、画面から独立した **API** として使えるようにする。次の段階で React の画面がこの API だけで作れること、Streamlit のデモも同じ処理を使って動き続けることがゴール。

達成方法（コード構成、API の設計、処理待ちの仕組み）は任せる。途中の確認は不要。

## API で使えるようにする機能

| 機能 | 内容 |
|---|---|
| マスター | 材料・工程・表面処理・価格方針・自社情報を返す |
| 形状の解析 | STEP または DXF（と、DXFなら板厚）を受け取り、解析する。**時間がかかるので、受け付けたらすぐに受付番号を返し、状態（待ち・処理中・完了・失敗）と結果を後から取れる**ようにする |
| 図面PDFの読み取り | 図面PDFを受け取り、条件を読み取る（解析と同じく受付番号方式）。APIキーがない環境では、使えないことを明確に返す |
| 見積の計算 | 解析結果と条件（材質・数量・表面処理・追加加工・特急・確定前の項目）から、見積を返す。画面と見積書と同じ金額（単価・小計・税・合計、概算かどうかと理由） |
| 見積書 | 宛先などを受け取り、見積書PDF（社外用、社内用の内訳）を作って返す。見積番号の採番と履歴への記録も行う |
| 類似見積 | 今回の条件から類似見積を返す（理由・違い・価格の比較つき） |
| 過去見積の履歴 | CSV の取り込み（列の対応づけ）、一覧・詳細、受注・失注の記録 |
| 3D表示用の形状 | STEP を、ブラウザで表示できる形式（glTF など）に変えて返す。React の画面で使う |

## 満たすこと

- **処理を2か所に書かない**：Streamlit の画面と API は、同じ処理の層（関数やクラス）を呼ぶ。今 `app.py` にある処理の組み立ては、その層に移す
- **入出力の型を決める**：リクエストとレスポンスは pydantic のモデルで定義し、OpenAPI の仕様（`/docs`）が自動で出る。今の `src/models.py` の既存フィールドと意味は壊さない
- **重い処理は裏で進める**：まずは同じプロセス内の簡単な仕組みでよい。ただし、あとで処理待ちの列（RQ・Celery など）に差し替えられる形にする。受付・状態・結果は、サーバーを再起動しても消えないようにする
- **データの置き場所を設定で変えられる**：アップロードしたファイル、解析結果、見積書、履歴の置き場所を環境変数で指定できる。既定はリポジトリ内の今の場所（履歴は `data/past_quotes/`）。あとでデータベースやファイル置き場のサービスに差し替えられる形にする
- **最低限の守り**：アップロードの大きさと種類の制限。エラーの応答に内部のパスや秘密情報を出さない。API の利用には、環境変数で設定する簡単な合言葉（トークン）を必須にできる（本格的なログインは段階3）
- **どこにでも置ける**：Dockerfile と docker-compose を用意し、API と Streamlit のデモを起動できる。クラウドの特定のサービスに頼らない（社内サーバーにも置けるように）
- **LLM**：このPhaseで LLM を新しく使う機能は作らない。図面PDFの読み取りは今の読み取り器をそのまま呼ぶだけ。テストは API を呼ばない（偽のクライアントを使う）

## 受入条件

| 項目 | 条件 |
|---|---|
| 機能 | 上の表の機能がすべて API で使える。FastAPI の TestClient で、機能ごとに端から端までのテストがある（小さな STEP・DXF・図面PDFを使う。図面PDFの読み取りは偽のクライアント） |
| 金額の一致 | 同じ入力なら、API・Streamlit の画面・見積書で金額が一致する（テスト） |
| 受付の速さ | 解析・読み取りの受付は、処理の長さに関係なくすぐ返る（目安0.5秒以内） |
| 再起動 | 処理中や完了した受付の状態と結果が、API を再起動しても取れる（テスト） |
| Streamlit | デモ画面が今までどおり動く（既存の画面のテストがパス） |
| 仕様書 | `/docs` で API の仕様が見られる。`analysis/api_design.md` に、機能ごとの呼び出しの流れ（例：アップロード → 解析の受付 → 状態の確認 → 見積 → 見積書）と、段階2・3で差し替える部分をまとめる |
| Docker | `docker compose up` で API とデモ画面が起動する。起動の手順を README に書く |
| 回帰 | `python -m pytest -q` がすべてパスし、STEP と DXF の評価（`--gate`）も合格のまま |

## 制約

- 解析・見積の結果を変えない（処理の場所を移すだけ）。変わる場合はテストと評価で示す
- 正解データとホールドアウトに関する `CLAUDE.md` の決まりはそのまま
- 金額を LLM に計算させない

## 対象外（今回はやらない）

- React の画面（段階2）
- ログイン、利用者ごとのデータの分離、PostgreSQL（段階3）
- クラウドへの配置
