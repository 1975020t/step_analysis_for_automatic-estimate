# 引き継ぎ：仕様書と操作マニュアルの作成

## 目的

ここまでに作ったデモ（STEP・DXF・図面PDFから見積を作り、見積書を出し、過去の類似見積を参照する）について、**関係者が読んで分かる資料一式** を作る。資料はこのブランチ（`docs/specifications`）に置き、**main にはマージしない**（PRも作らない）。

**コードは変えない**（資料のための画面写真を撮るスクリプトなどを足すのはよい）。**LLM API は使わない**。

## 作る資料

`docs/` フォルダに Markdown で作る。図は Mermaid（GitHub上でそのまま図になる）と画像（`docs/images/`）を使う。**図と画像を多めに入れて、読んで分かる資料にする。**

| 資料 | ファイル | 読む人 | 中身 |
|---|---|---|---|
| 目次 | `docs/README.md` | 全員 | 資料の一覧と、どれを読めばよいか |
| 要件定義書 | `docs/01_要件定義書.md` | 経営者・顧客・開発者 | 何のためのシステムで、何ができるべきか |
| 設計書 | `docs/02_設計書.md` | 開発者 | どう作っているか（**実装のロジック**） |
| 画面設計書 | `docs/03_画面設計書.md` | 全員 | 画面ごとの項目・操作・表示（画面の写真。**実装方法は書かない**） |
| 操作マニュアル | `docs/04_操作マニュアル.md` | 見積担当者（プログラミングの知識がない人）と、導入する人 | セットアップから日々の操作まで |

### 要件定義書

- 背景と目的（板金の見積業務の課題、このシステムで何を変えるか）
- 対象ユーザーと利用場面
- **業務の流れ**：今の見積業務と、システム導入後の流れ（図）
- 範囲：入力（STEP・DXF・図面PDF）と出力（見積書）、扱う部品（形状のレベル）、扱わないもの
- **機能要件**：番号をつけて一覧にする（例：FR-01 STEPの解析）。それぞれ、何を入力して何が得られるか
- **非機能要件**：精度（目標と、評価で確かめた実績）、処理時間、LLMの使い方の方針（金額はLLMに計算させない、など）、データの扱い、セキュリティ
- 前提と制約（合成データで評価していること、実データでの評価はまだ、など）
- 今後の課題（クラウドへの移行、図面PDF読み取りの懸念点、実データでの評価、画面の作り直し）
- 用語集（図番、改訂、展開、Kファクター、曲げ線、表面処理、概算、要確認・未登録 など）

### 設計書

**実装のロジックを中心に書く。** 数式、判定の条件、処理の順番、判定に使うしきい値を、コードを読まなくても分かるように。

- システム構成（画面・API・処理の層・マスター・データ・外部のLLM）の図
- 主な処理の流れ（アップロードから見積書まで）のシーケンス図
- 機能ごとの実装ロジック（それぞれ図を入れる）
  - STEPの解析：板厚の認識、表裏の面の対応、曲げの認識、展開（グラフによる展開、Kファクター）、穴の数え方、自己検算と結果の状態（確定・概算・解析不可）の決め方、理由コード
  - 展開図DXFの解析：図形の正規化、端点のまとめ方、線の役割の判定、部品の特定、問題（開いた輪郭・複数部品）の検出、状態の決め方
  - 図面PDFの読み取り：画像の作り方、LLMに渡すもの・返させるもの（システムプロンプトの要点、出力の形）、ルールでの値の決め方、2回読みの照合、要確認の決め方
  - 見積の計算：各明細の計算式、`charge_scope`、表面処理・特急割増・粗利率、概算になる条件
  - 見積書：記載項目、端数処理、見積番号の採番、社外用と社内用の違い
  - 類似見積：区分（リピート・同じ顧客・他の顧客）、条件の判定、並べ方、価格の比較（過去の出し値の水準）
  - API：機能ごとのエンドポイントと、受付番号方式の処理（状態の移り変わりの図）
- **データ設計**：マスター（各CSVの列と意味）、過去見積の履歴、保存するファイル
- 評価の仕組み：ゴールデンデータ（STEP・DXF・図面PDF）、評価ハーネス、判定の区分（確定で正解・危険誤答など）、ホールドアウトの考え方。評価の結果（数字は `analysis/` のレポートから）
- LLMを使う箇所の一覧（どこで・何を入力し・何を出力するか・使わない箇所）
- フォルダ構成：**クラウドに移す予定なので、詳しくは要らない。** 主なモジュールと役割の短い表だけでよい

### 画面設計書

- 画面の一覧と、画面の移り変わり（図）
- 画面ごとに：**実際の画面の写真**、表示項目と入力項目の表（項目名・必須かどうか・説明・入力の例）、操作と結果、エラーや注意の表示、状態の表示（確定・要確認・未登録・記載なし、概算）
- 見積書（確定・概算・社内用）の見本の画像と、記載項目の説明
- **実装方法（Streamlitのコードなど）は書かない**

### 操作マニュアル

- 動作環境
- **セットアップを詳しく**（ユーザーは Windows・PowerShell。`CLAUDE.md` の環境の節を参照）：Pythonの入れ方、リポジトリの取得、仮想環境、依存パッケージの導入、APIキーの設定（任意。無いと何が使えないか）、自社情報の設定（`data/company.local.csv`）、起動（デモ画面、API、Docker）。つまずきやすい所（CadQuery の導入、Pythonの版など）
- **操作を手順どおりに、画面の写真つきで**
  - STEPから見積を作る
  - 展開図DXFから見積を作る（板厚の入力）
  - 図面PDFを合わせて使う（読み取った条件の確認と修正）
  - 見積書を出力する（確定・概算）
  - 類似見積を見る
  - 受注・失注を記録する、過去見積を取り込む
  - マスター（単価・材質・表面処理など）を変える
- 画面の表示の意味（確定・要確認・未登録・記載なし、概算とは何か）
- よくある質問とトラブル対応
- 開発者向けの付録：API の使い方の概要（`/docs` の見方と、呼び出しの例）

## 作り方の条件

- **書く内容は、今のコードと資料で確かめる。** 数字（精度・処理時間など）は `analysis/` のレポートなどから取り、推測で書かない。資料どうしで内容が食い違わないようにする
- **画面の写真は実物を撮る**（デモ画面を起動し、Playwright などで撮影する。Chromium は入っている）。データは開発用データ（`golden_data`、`dxf_data`、`pdf_data`）と架空の宛先を使う。図面PDFの読み取りの画面は、LLM を呼ばずに撮れる方法（記録済みの応答、偽のクライアントなど）を使う。撮影の手順はスクリプトにして残す（`docs/scripts/` など）
- 既存の画像（`analysis/*.png` など）は使ってよい
- 図の文字と説明は日本語。読む人に合わせて、専門用語には説明をつける（特に操作マニュアル）
- 秘密情報（APIキーなど）を資料に書かない
- ホールドアウトの正解値のファイル（`golden/datasets/*holdout*.json`）は開かない
- まだできていないこと・分かっている限界は、正直に書く（例：図面PDF読み取りの懸念点、実データでの評価はまだ）

## 完了時

- `docs/` 一式（資料・画像・撮影のスクリプト）をこのブランチにコミットしてプッシュする。main へのPRは作らない
- 最後に、資料の一覧と、それぞれの図・画像の数を報告する
