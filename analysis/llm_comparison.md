# ルールベースとLLM（Claude API）の比較

2026-09-27。解析ロジック改善（汎用展開＋自己検算）と並行して、Claude API を解析に使う2方式を試し、ルールベースのみと比べた。

## 結論

**採用はルールベースのみ（LLMは既定の解析経路に入れない）。**

- 新しいルールベースは開発データ508件・ホールドアウト200件・追加の検証用シード2000件のすべてで「確定で正解」。LLMが直すべき誤りが残っていない
- LLMを足しても解析成功率は上がらず、正しい値を「概算」にする誤警報だけが増えた（レビュー方式で26%、独立カウント方式で77〜84%）
- 処理時間は1件あたり0.2秒 → 5.9〜14.8秒（独立カウント方式は受入条件の10秒を超える）
- 旧ロジックに対しては、LLMレビューが危険誤答を24件→13件に減らしたが、0にはできなかった。危険誤答をなくしたのは幾何の自己検算（展開面積と体積÷板厚、切断長と切断面積÷板厚の一致など）である

## 試した方式

どちらも LLM は数値を出さない・変えない。結果を「より慎重な方向」（success → partial ＝概算、または unsupported）にだけ動かせる。

| 方式 | クラス | Claudeに渡すもの | 判定への反映 |
|---|---|---|---|
| レビュー | `src.llm_assisted_analyzer:LLMAssistedAnalyzer` | ルールベースの結果の要約（値、曲げ、展開方式、品質、警告） | accept / downgrade（概算） / reject |
| 独立カウント（クロスチェック） | `src.llm_assisted_analyzer:LLMCrossCheckAnalyzer` | B-Rep面の一覧（種類、面積、法線・軸、半径、円筒の角度範囲、隣接面）。ルールベースの結果は渡さない | Claude が数えた曲げ数・ヘム数・穴数がルールベースと1つでも違えば概算 |

モデルは `claude-sonnet-5`（`.env` の `ANTHROPIC_MODEL`）。

## 結果（開発データ golden_v1 の各レベル先頭20件、計100件、誤差±10%）

| 構成 | 解析成功 | 確定で正解 | 正解だが概算 | 危険誤答 | 平均処理時間 | 1件あたりトークン（入力/出力） | レポート |
|---|---:|---:|---:|---:|---:|---:|---|
| 新ルールベースのみ（採用） | 100/100 | 100 | 0 | 0 | 0.2s | 0 / 0 | [rule20](llm_eval/rule20.md) |
| 新ルールベース＋レビュー | 100/100 | 74 | 26 | 0 | 5.9s | 1,520 / 355 | [review20](llm_eval/review20.md) |
| 新ルールベース＋独立カウント（プロンプトA） | 99/100 ※ | 22 | 77 | 0 | 13.8s | 4,192 / 1,055 | [cross20b](llm_eval/cross20b.md) |
| 新ルールベース＋独立カウント（プロンプトB：曲げの数え方を詳述） | 100/100 | 16 | 84 | 0 | 14.8s | 4,265 / 1,032 | [cross20](llm_eval/cross20.md) |
| 旧ロジックのみ（参考） | 42/100 | 23 | 19 | **24** | 0.5s | 0 / 0 | [base20](llm_eval/base20.md) |
| 旧ロジック＋レビュー（参考） | 40/100 ※ | 22 | 18 | **13** | 7.1s | 1,528 / 465 | [basereview20](llm_eval/basereview20.md) |

※ 解析不可の計4件（cross20b の1件、basereview20 の3件）は、評価の途中で Claude API のクレジット残高が尽き、HTTP 400（credit balance is too low）になったもの。LLMの判断ではない。トークン数はAPIを実際に呼んだ件の平均。

### 独立カウントでのLLM自身の正答率

Claude が面の一覧から数えた値が正解と一致した割合（プロンプトA、99件）：曲げ数 41%、ヘム数 69%、穴数 38%、3つとも一致 22%。
Lv0（平板）でも穴数は11/20件しか合わず、角穴の側面（平面4枚）を外周の一部と判断する誤りが目立った。Lv3 では曲げ数・穴数ともほぼ合わない（曲げの内外2枚の円筒を別々に数える等）。面の数が数十〜百を超える隣接グラフを文章として読ませて数える作業は、幾何計算より大幅に不正確だった。

## LLMの使いどころ（今後）

今回の合成データでは効果がなかったが、次の場面では役に立つ可能性がある。いずれも数値は幾何計算側で出し、LLMは説明や分類に限る。

- 自己検算が不一致で「概算」になった部品について、担当者向けに原因（どの面・どの特徴が合わないか）を説明する文面を作る
- 実CADデータで出てくる対象外形状（成形、ルーバー等）の分類と、見積担当への確認事項の提示
- 図面・注記など、形状以外の情報（材質、表面処理、数量）の読み取り

## 再現手順

```
python scripts/evaluate_golden.py --data golden_data --tolerance 0.10 --limit 20 --workers 4 --analyzer src.llm_assisted_analyzer:LLMAssistedAnalyzer
python scripts/evaluate_golden.py --data golden_data --tolerance 0.10 --limit 20 --workers 4 --analyzer src.llm_assisted_analyzer:LLMCrossCheckAnalyzer
```

応答は `.claude_cache/` に保存される（Git管理外）。部品ごとの結果（LLMの数えた値 `llm_bend_count` 等を含む）は `analysis/llm_eval/*.csv`。
