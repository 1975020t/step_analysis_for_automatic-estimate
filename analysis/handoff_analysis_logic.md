# 引き継ぎ：解析ロジック改善

## 最終ゴール

STEP形式の板金部品から、見積に使う値（板厚・展開面積・切断長・穴数・曲げ数、およびヘムの有無）を、**ゴールデンデータの全レベル（Lv0〜Lv4）で安定して正しく出せる解析ロジック** を完成させる。

達成方法（アルゴリズム、ルールベース／LLMの使い分け、コード構成、作業順序）は任せる。途中で設計の確認は不要なので、判断して進めてよい。

## 受入条件

次をすべて満たしたら完了とする。

| 項目 | 条件 |
|---|---|
| 解析成功 | 各レベル（**Lv0〜Lv4それぞれ**）で **90%以上**。成功とは、板厚・展開面積・切断長の誤差が **±10%以内**、かつ曲げ数・穴数・ヘム（170°以上の曲げ）の数が正解と一致すること |
| 危険誤答 | 各レベルで **2%以下**。値が誤っているのに見積が「概算」表示にならないもの |
| 汎化 | 下記の **ホールドアウト（`holdout_v1`：seed=2、各レベル40件、計200件）** でも上の2条件を満たす。1レベル40件なので、解析成功90%は失敗4件まで、危険誤答2%以下は実質0件を意味する |
| 回帰 | `python -m pytest -q` がすべてパスする |
| 性能 | 1部品あたりの平均処理時間が5秒以内（LLMを使う場合はAPIの待ち時間込みで10秒以内） |

判定コマンド（開発データ、`--gate` は未達なら終了コード1）:

```
python scripts/generate_golden.py --per-level 100 --seed 1 --out golden_data
python scripts/evaluate_golden.py --data golden_data --verify-frozen --tolerance 0.10 --gate --report analysis/golden_eval_latest.md
```

最終判定（ホールドアウト。開発の最後に実行する）:

```
python scripts/generate_golden.py --per-level 40 --seed 2 --no-curated --out golden_holdout
python scripts/evaluate_golden.py --data golden_holdout --verify-frozen golden/datasets/holdout_v1.json --tolerance 0.10 --gate --report analysis/golden_eval_holdout.md
```

## 完了時に残すもの

- 改修したコードとテスト
- `analysis/golden_eval_latest.md`（開発データ）と `analysis/golden_eval_holdout.md`（ホールドアウト）の評価レポート
- 採用した方式の説明（README の「解析方式」を更新）
- LLMを使った場合：使いどころ、効果（ルールベースのみとの比較）、1部品あたりのトークン数と処理時間

## 現状（参考情報）

誤差±10%での現行ロジックの結果（全文は [golden_eval_baseline_10pct.md](golden_eval_baseline_10pct.md)）:

| レベル | 形状 | 解析成功 | 危険誤答 |
|---|---|---:|---:|
| Lv0 | 平板 | 100% | 0% |
| Lv1 | 平行曲げ（L/U/Z/ハット/多段） | 44% | 0% |
| Lv2 | 底面＋1段フランジ（トレー） | 14% | 63% |
| Lv3 | 多段フランジ | 6% | 64% |
| Lv4 | ヘム（180°曲げ） | 55% | 0% |

これまでの調査で分かっていること（方針を縛るものではない）:

- 板厚・曲げ数・ヘムの検出は全レベルでほぼ正確。外れているのは主に **展開** と **曲げ部品の穴数**
- 展開（`src/sheetmetal_unfold.py`）は「平板」「平行曲げ」「底面に直接付くフランジのみのトレー」のパターン別処理で、外形を長方形と仮定している。2段目以降のフランジやフランジ上の穴が反映されない
- 曲げ部品の穴数は円筒面の数で数えているため、長穴（両端が半円筒2面）を2穴と数える。Lv1・Lv4の不合格はほぼこれが原因
- 信頼度が計算方式の種類で決まり、検算で決まっていないため、外れても high のまま出る（危険誤答の原因）
- 詳細な分析は [golden_data_design.md](golden_data_design.md)

## ルールベース：初回の改善方向（推奨）

ここまでの検証から、まず取り組むべき方向を示す。より良い方法が見つかれば変えてよい。

### 1. 展開を「面グラフをたどる汎用展開」に置き換える（最優先）

3つのパターン別処理（`src/sheetmetal_unfold.py`）をやめ、1つのアルゴリズムで全形状を展開する。参考実装が [prototypes/unfold_prototype.py](prototypes/unfold_prototype.py) にある（約100行、本番品質ではない）。

考え方:

1. 表裏ペアのうち **片側の面だけ**（平面と曲げの円筒面）を使う。最大面積の平面を基準面にする
2. 隣接グラフを幅優先でたどる。「平面→円筒→平面」と曲げを通過するたびに、子側の変換を次のように合成する
   `U = 平行移動(n × BA) ∘ 回転(曲げ軸, −θ)`、`BA = θ × (内R + K × t)`
   - 回転角は、子の平面の法線が親の平面の法線に一致する向き（符号を含めて算出する）
   - `n` は、基準面内で曲げ軸に垂直かつ親から子へ向かう単位ベクトル
   - これはゴールデンデータ生成器が「平板を曲げる」ときの変換のちょうど逆で、理論上は厳密に一致する
3. 各平面の外周ワイヤーと穴ワイヤーを基準面の2Dへ写す。曲げ部は、親側と子側の2本の接線エッジで挟まれた帯として写す
4. すべての領域を合成して展開図を作る。**面積＝ポリゴン面積、切断長＝全輪郭長、穴数＝内側ループの数**

参考実装の実績（golden_v1、Lv1〜Lv4の407件、誤差±10%かつ穴数一致）:

| Lv1 | Lv2 | Lv3 | Lv4 | 合計 |
|---:|---:|---:|---:|---:|
| 101/104 | 93/102 | 95/101 | 96/100 | **385/407（95%）** |

Lv0は現行の平板処理で100%。確認した失敗例でも面積の誤差は0.1%未満で、外れていたのは切断長と穴数だった。

### 2. 参考実装で残っている失敗への対処

残り22件の失敗は、確認した範囲では主に **合成時に残る細いすき間（スリバー）** が原因だった。

- 曲げ帯と平面のあいだに0.01mm未満のすき間が残ると、それが余分な輪郭として切断長を水増しし、ときに小さな「穴」として数えられる
- 参考実装は `buffer(ε)` → `buffer(−ε)` で閉じているが、固定のε（0.01mm）では閉じきれないケースがある
- 対策の候補：帯の頂点を隣接する平面の頂点へ吸着させる／εを板厚や公差に連動させる／極小面積の内側ループを穴として数えない（ただし実在の小径穴を消さないこと）
- エッジは24点でサンプリングしているため、円弧を含む輪郭の長さはわずかに短くなる。必要なら円弧を解析的に扱う

### 3. 自己検算で信頼度と status を決める（危険誤答の対策）

展開の成否を方式名で判定せず、次の検算を通過したときだけ `success` / `high` にする。通らなければ `partial`（概算）にする。

- **面積**：`体積 ÷ 板厚 + Σ θ × t × (K − 0.5) × 曲げ長さ` と展開面積が一致する（K=0.5なら体積÷板厚と厳密に一致）
- **切断長**：`切断側面の総面積 ÷ 板厚 + Σ（曲げ端面ごとに θ × t × (K − 0.5)）` と展開図の全輪郭長が一致する。切断側面は、表裏ペアにも曲げ円筒にも属さない面
- 展開図が単一ポリゴンで、自己交差や重なりがない
- 全平面ペアが展開に含まれている（たどり残しがない）

許容差は1%程度から始め、ゴールデンデータの誤差分布を見て決める。上記2のスリバーはこの検算で検出できる。

### 4. 実装上の注意

- **片側を守る**：隣接をたどるときに裏側の面へ移らないこと（表裏ペアの相手はたどらない）
- **ヘム**：180°前後の曲げでも同じ変換で展開できる。`bend_evidence` に角度を正しく残すこと（ヘム検出の判定に使われる）
- **閉路**：箱のように展開経路が複数ある形では、最初に到達した経路を採用し、別経路での位置ずれを検算に使う
- **円筒面の分割**：CADによっては1つの曲げや穴の円筒面が複数に分かれる。面の数ではなく、軸と半径でまとめる
- **性能**：表裏ペアの探索（`match_surface_pairs`）は全面の総当たりで、`face.distance` が重い。多穴の平板で10秒を超える。法線と位置で候補を絞る
- **既存経路との統合**：平板は現行処理で100%なので、汎用展開に一本化するか併存させるかは任せる。どちらの場合もLv0の成績を落とさないこと

## 制約

- **正解データを変えて合格させない**：`golden/sheetgen.py`、`golden/sampler.py`、`golden/datasets/`（`golden_v1.json`・`holdout_v1.json`）は変更しない。生成器の不具合を見つけた場合は、新しいデータセット版（`golden_v2`）を作り、`golden_v1` は残して報告する
- **ホールドアウトで調整しない**：正解値は `golden/datasets/holdout_v1.json` に凍結済み。このファイルは開かず、seed=2 のデータは最終判定のときだけ生成する。結果が悪くても、ホールドアウトの部品を見て直さず、開発データ側で原因を探す
- **既存インターフェースを維持する**：`SheetMetalAnalysis` のフィールド、`status` の意味、`metric_quality` の形式（UIと見積が依存）
- **金額はLLMに計算させない**：金額はマスターCSVとルールで決定論的に計算する
- 評価レポートの数字はハーネスの出力をそのまま使い、推測で書かない

## LLM（Claude API）の利用

ルールベースとの併用・比較を含めて試してよい。形状データ（面・寸法・座標などの解析情報、画像）をClaude APIへ送ることはユーザー承認済み。

- 準備済みのもの：
  - `src/claude_api.py`：クライアント。キーは環境変数 `ANALYSIS_ANTHROPIC_API_KEY`（`.env` でも可。`ANTHROPIC_API_KEY` も読む）、モデルは `ANTHROPIC_MODEL`
  - `src/llm_assisted_analyzer.py`：サンプルの解析器。ルールベースの結果をClaudeがレビューし、慎重な方向にのみ変更する。作り替えてよい
  - `scripts/check_claude_api.py`：APIキーの疎通確認
- ハーネスで評価する：`--analyzer module:Class` で解析器を差し替える。`--repeat 3` で結果のばらつき、`--limit` で件数を絞った試行ができる。トークン数はレポートに自動で集計される
- キャッシュ：`CLAUDE_CACHE_MODE=record`（既定）では同じ問い合わせの応答を `.claude_cache/` に保存して再利用する。**pytest ではAPIを呼ばず**、記録済みの応答か偽のクライアントを使う（例：`tests/test_claude_api.py`）
- APIキーが未設定の場合は、LLMを使う評価を飛ばして進め、完了報告にその旨を書く
- LLMの出力をそのまま数値に使わない。数値を出す場合は、幾何計算による検算を通すこと

## 対象外（今回はやらない）

- 実CADのSTEPの癖（面の分割、微小面）への対応：実データ入手後
- 成形加工（ルーバー、エンボス、バーリング、タップ）、圧入部品、曲げを横切る穴
- 密着ヘム（すき間のない折り返し）：ゴールデンデータは内R 0.5t〜1t のオープンヘムのみ
- 見積ロジック（価格モデル）の改修。ヘムの加工費を別工程として扱う件は別途
