# 引き継ぎ：解析ロジック改善（Lv0〜Lv3 解析成功90%）

## 1. ゴール

ゴールデンデータ（`golden_v1`、508件）で、**Lv0〜Lv3 の各レベルとも解析成功率90%以上** を達成する解析ロジックを作る。

### 受入条件

| 項目 | 条件 |
|---|---|
| 解析成功 | 板厚・展開面積・切断長の誤差が **±10%以内**、曲げ数が一致、穴数が一致。Lv0〜Lv3の **各レベルで90%以上** |
| 危険誤答 | 値が誤っているのに見積が「概算」表示にならない割合。**各レベルで2%以下**（Lv4を含む） |
| Lv4（ヘム） | **95%以上を解析不可（unsupported）として弾く** |
| 汎化 | 最終判定は **seed=2 のホールドアウト** で行い、上の3条件を満たすこと（手順は8章） |
| 回帰 | 既存テストがすべてパスすること |
| 処理時間（目安） | 1件あたり平均5秒以内（現状0.2〜1秒） |

判定コマンド（開発中）:

```
python scripts/evaluate_golden.py --data golden_data --verify-frozen --tolerance 0.10 --gate --report analysis/golden_eval_latest.md
```

`--gate` は条件を満たさないと終了コード1を返す。

> **穴数について（要確認事項）**：穴数の一致を成功条件に含めるかで難度が大きく変わる。本資料では含める前提にしているが、ユーザーの判断で `--holes ignore` に変更されうる。どちらの場合も穴数の一致率はレポートに出る。

## 2. 現状（出発点）

誤差±10%での現行ロジックの結果（全文は [golden_eval_baseline_10pct.md](golden_eval_baseline_10pct.md)）:

| レベル | 解析成功（穴数一致を含む） | 解析成功（穴数を除く） | 危険誤答 |
|---|---:|---:|---:|
| Lv0 平板 | 100% | 100% | 0% |
| Lv1 平行曲げ | 44% | 100% | 0% |
| Lv2 底面＋1段フランジ | 14% | 61% | 63% |
| Lv3 多段フランジ | 6% | 22% | 64% |
| Lv4 ヘム（弾くべき） | 解析不可 0% | — | 0%（偶然「概算」表示になっているだけ） |

- 板厚と曲げ数は全レベルで正確。**認識部分（`sheetmetal_recognition.py`）は概ね良好**
- 失敗は **展開** と **穴の数え方** に集中している

## 3. 失敗の原因

### 3.1 展開がパターン別の特殊処理になっている（`sheetmetal_unfold.py`）

- 平行曲げ：外形を **長方形と仮定**（面積÷幅で長さを出す）。部分幅フランジや切欠きで切断長が外れる
- トレー（`_branched`）：**底面に直接付くフランジだけ** を、それぞれ **長方形** として貼り付ける。2段目以降のフランジは黙って無視され、フランジ上の穴も外形に反映されない
- その結果、Lv2・Lv3で面積・切断長が大幅に小さいまま「success・high」で出る（危険誤答の主因）

### 3.2 曲げ部品の穴を円筒面の数で数えている（`sheetmetal_recognition.hole_components`）

- 長穴は両端の半円筒が別々の面になるため、**長穴1つを穴2つと数える**。Lv1の穴数不一致57件はすべて長穴・角穴を含む部品
- 曲げ部品の穴数の信頼度が常に `medium` になり、値が正しくても見積が必ず「概算」になる
- CADによっては丸穴も半円筒2枚で出力されるため、実データではさらに悪化しうる

### 3.3 対象外形状を検出していない

- ヘム（約180°曲げ）を通常の曲げとして通してしまう。READMEの仕様では対象外

### 3.4 信頼度が「方式」で決まり、「検算」で決まっていない

- 展開方式の名前で high/medium を付けているため、特殊処理が外れても high のまま出る

## 4. 推奨アプローチ（ルールベース）

合成データは理想的なCADモデルであり、曖昧さによる失敗ではなく計算方法の不足による失敗なので、**ルールベースで達成できる見込みが高い**。LLMは必須ではない。

### 4.1 汎用展開（面グラフの全域木による展開）

1. 表裏ペアのうち片側の面（平面と曲げ円筒面）を「スキン面」として選ぶ。平面の直線部の長さは表裏で同じなので、どちらの側でもよい
2. 最大面積の平面を基準面とし、スキン面の隣接グラフを幅優先で辿る
3. 曲げ円筒面を通過するたびに、その曲げの剛体変換を合成する：曲げ軸まわりに曲げ角だけ戻し、曲げ代 BA = θ(R + K·t) の帯として平面に展開する
4. 各平面の実輪郭（外周ワイヤー＋穴ワイヤー）を累積変換で基準面の2Dへ写す。曲げ面は、幅 = 曲げの軸方向長さ、長さ = BA の帯として写す
5. 全ポリゴンを shapely で合成し、外周と内側ループから面積・切断長・穴数を求める
6. 閉路（箱のように展開経路が複数ある形）では、最初に到達した経路を採用し、他の経路との食い違いを検算に使う

これで平板・平行曲げ・トレー・多段フランジ・斜めフランジを、1つのアルゴリズムで処理できる。既存の3パターンは、この方式で置き換えるか、検算用に残す。

### 4.2 穴数

展開後の2Dポリゴンの **内側ループ数** で数える（平板ではすでにこの方式で100%）。

### 4.3 対象外の検出

- 曲げ角がおおむね170°以上、または展開後に自己交差する形状は `unsupported`（理由コードを新設してよい。例：`HEM_DETECTED`）
- 既存の理由コード体系に合わせ、`reason_codes` とメッセージで理由を示す

### 4.4 自己検算による信頼度

次の検算をすべて通過したときだけ `high` / `success` にする。通らなければ `partial`（概算）にする。

- 展開面積 ≒ 体積 ÷ 板厚（K=0.5 なら厳密一致。K≠0.5 の場合は曲げ代の差分を補正して比較する）
- 切断長 ≒ 切断側面の総面積 ÷ 板厚
- 展開図が単一ポリゴンで、自己交差がない

これが **危険誤答2%以下** を担保する中心的な仕組みになる。

### 4.5 性能

面ペア探索はO(n²)で、多穴の平板（225穴）で約12秒かかる。隣接情報やバウンディングボックスで候補を絞る。

## 5. 進め方

各フェーズで pytest と評価ハーネスを回し、レポートを `analysis/golden_eval_latest.md` に残してコミットする。

| フェーズ | 内容 | 確認すること |
|---|---|---|
| 0 | 環境構築、データ生成、現状の再現 | 現状値が2章と一致する |
| 1 | 穴数を2D内側ループ数に変更 | Lv1の解析成功が大幅に上がる |
| 2 | 汎用展開の実装（4.1） | Lv2・Lv3の面積・切断長誤差が下がる |
| 3 | 自己検算による信頼度（4.4） | 危険誤答が2%以下になる |
| 4 | ヘム検出（4.3） | Lv4の解析不可が95%以上 |
| 5 | 性能改善、コード整理、ドキュメント更新 | 全テストパス、処理時間 |
| 6 | ホールドアウトで最終判定（8章） | 受入条件をすべて満たす |

失敗した部品は `golden_data/results.csv` で抽出し、`scripts/render_golden.py` で形状を見て原因を確認する。

## 6. 守ること

- **正解データを変えて合格させない**：`golden/sheetgen.py`、`golden/sampler.py`、`golden/datasets/golden_v1.json` は変更しない。生成器の不具合を見つけた場合は作業を止めて報告する
- **ホールドアウトで調整しない**：seed=2 のデータは最終判定まで生成・参照しない
- **既存インターフェースを壊さない**：`SheetMetalAnalysis` のフィールド、`status` の意味、`metric_quality` の形式を維持する（UI・見積が依存）
- **金額計算にLLMを使わない**
- 評価レポートの数字はハーネスの出力をそのまま使い、推測で書かない

## 7. LLM（Claude API）を使う場合

### 使ってよい範囲

- 形状の分類・判断の補助（例：対象外形状の候補を挙げる、展開経路の選択を補助する）
- **座標・面積・長さなどの数値はLLMに出させない**。数値は必ず幾何計算で出し、4.4の検算を通す

### 情報保護（要ユーザー承認）

- これまでの方針は「形状データは外部APIに送らない」。LLMに形状由来の情報を送る場合は、**送信する項目をユーザーが承認するまで実装しない**。承認後、その範囲を README と本資料に明記する

### テストの進め方

- 解析器を `module:Class` の形で実装し、`--analyzer` で差し替えて同じハーネスで評価する
- APIキーは `.env` の `ANTHROPIC_API_KEY` に置く（`.env` はGit管理外）。コードやログにキーを出さない
- **pytest ではAPIを呼ばない**：LLMの応答を記録したファイルを再生して判定する（記録・再生の仕組みを用意する）
- 精度評価は `--repeat 3` で同じ部品を複数回解析し、成功率とばらつきを見る
- 1件あたりの費用・処理時間を記録し、ルールベースと比較する
- 開発中は `--limit` で件数を絞り、費用を抑える

## 8. 最終判定（ホールドアウト）

開発が完了したら、一度だけ次を実行する。

```
python scripts/generate_golden.py --per-level 100 --seed 2 --out golden_holdout
python scripts/evaluate_golden.py --data golden_holdout --tolerance 0.10 --gate --report analysis/golden_eval_holdout.md
```

`golden_holdout/` はGit管理外（`.gitignore` 設定済み）。seed=2 の結果が開発データより大きく悪い場合は、開発データへの過剰な合わせ込みを疑う。その場合もホールドアウトの部品を見て調整せず、開発データ側で原因を探す。

## 9. 対象外（今回はやらない）

- 実CADのSTEPの癖（面の分割、微小面）への対応：実データ入手後
- 成形加工（ルーバー、エンボス、バーリング、タップ）、圧入部品、曲げを横切る穴
- K≠0.5 の正解データ（生成器は対応しているが、体積一致による自己検証が使えないため未整備）
- 見積ロジック（価格モデル）の改修
