# 引き継ぎ：解析ロジック改善

## 最終ゴール

STEP形式の板金部品から、見積に使う値（板厚・展開面積・切断長・穴数・曲げ数、およびヘムの有無）を、**ゴールデンデータの全レベル（Lv0〜Lv4）で安定して正しく出せる解析ロジック** を完成させる。

達成方法（アルゴリズム、ルールベース／LLMの使い分け、コード構成、作業順序）は任せる。途中で設計の確認は不要なので、判断して進めてよい。

## 受入条件

次をすべて満たしたら完了とする。

| 項目 | 条件 |
|---|---|
| 解析成功 | 各レベル（**Lv0〜Lv4それぞれ**）で **90%以上**。成功とは、板厚・展開面積・切断長の誤差が **±10%以内**、かつ曲げ数・穴数・ヘム（170°以上の曲げ）の数が正解と一致すること |
| 危険誤答 | 各レベルで **2%以下**。値が誤っているのに見積が「概算」表示にならないもの |
| 汎化 | 下記の **ホールドアウト（seed=2）** でも上の2条件を満たす |
| 回帰 | `python -m pytest -q` がすべてパスする |
| 性能 | 1部品あたりの平均処理時間が5秒以内（LLMを使う場合はAPIの待ち時間込みで10秒以内） |

判定コマンド（開発データ、`--gate` は未達なら終了コード1）:

```
python scripts/generate_golden.py --per-level 100 --seed 1 --out golden_data
python scripts/evaluate_golden.py --data golden_data --verify-frozen --tolerance 0.10 --gate --report analysis/golden_eval_latest.md
```

最終判定（ホールドアウト。開発の最後に実行する）:

```
python scripts/generate_golden.py --per-level 100 --seed 2 --out golden_holdout
python scripts/evaluate_golden.py --data golden_holdout --tolerance 0.10 --gate --report analysis/golden_eval_holdout.md
```

## 完了時に残すもの

- 改修したコードとテスト
- `analysis/golden_eval_latest.md`（開発データ）と `analysis/golden_eval_holdout.md`（ホールドアウト）の評価レポート
- 採用した方式の説明（README の「解析方式」を更新）
- LLMを使った場合：使いどころ、効果（ルールベースのみとの比較）、1部品あたりのトークン数と処理時間

## 現状（参考情報）

誤差±10%での現行ロジックの結果（全文は [golden_eval_baseline_10pct.md](golden_eval_baseline_10pct.md)）:

| レベル | 形状 | 解析成功 | 危険誤答 |
|---|---|---:|---:|
| Lv0 | 平板 | 100% | 0% |
| Lv1 | 平行曲げ（L/U/Z/ハット/多段） | 44% | 0% |
| Lv2 | 底面＋1段フランジ（トレー） | 14% | 63% |
| Lv3 | 多段フランジ | 6% | 64% |
| Lv4 | ヘム（180°曲げ） | 55% | 0% |

これまでの調査で分かっていること（方針を縛るものではない）:

- 板厚・曲げ数・ヘムの検出は全レベルでほぼ正確。外れているのは主に **展開** と **曲げ部品の穴数**
- 展開（`src/sheetmetal_unfold.py`）は「平板」「平行曲げ」「底面に直接付くフランジのみのトレー」のパターン別処理で、外形を長方形と仮定している。2段目以降のフランジやフランジ上の穴が反映されない
- 曲げ部品の穴数は円筒面の数で数えているため、長穴（両端が半円筒2面）を2穴と数える。Lv1・Lv4の不合格はほぼこれが原因
- 信頼度が計算方式の種類で決まり、検算で決まっていないため、外れても high のまま出る（危険誤答の原因）
- 詳細な分析は [golden_data_design.md](golden_data_design.md)

## 制約

- **正解データを変えて合格させない**：`golden/sheetgen.py`、`golden/sampler.py`、`golden/datasets/golden_v1.json` は変更しない。生成器の不具合を見つけた場合は、新しいデータセット版（`golden_v2`）を作り、`golden_v1` は残して報告する
- **ホールドアウトで調整しない**：seed=2 のデータは最終判定のときだけ生成する。結果が悪くても、ホールドアウトの部品を見て直さず、開発データ側で原因を探す
- **既存インターフェースを維持する**：`SheetMetalAnalysis` のフィールド、`status` の意味、`metric_quality` の形式（UIと見積が依存）
- **金額はLLMに計算させない**：金額はマスターCSVとルールで決定論的に計算する
- 評価レポートの数字はハーネスの出力をそのまま使い、推測で書かない

## LLM（Claude API）の利用

ルールベースとの併用・比較を含めて試してよい。形状データ（面・寸法・座標などの解析情報、画像）をClaude APIへ送ることはユーザー承認済み。

- 準備済みのもの：
  - `src/claude_api.py`：クライアント。キーは `.env` の `ANTHROPIC_API_KEY`、モデルは `ANTHROPIC_MODEL`
  - `src/llm_assisted_analyzer.py`：サンプルの解析器。ルールベースの結果をClaudeがレビューし、慎重な方向にのみ変更する。作り替えてよい
  - `scripts/check_claude_api.py`：APIキーの疎通確認
- ハーネスで評価する：`--analyzer module:Class` で解析器を差し替える。`--repeat 3` で結果のばらつき、`--limit` で件数を絞った試行ができる。トークン数はレポートに自動で集計される
- キャッシュ：`CLAUDE_CACHE_MODE=record`（既定）では同じ問い合わせの応答を `.claude_cache/` に保存して再利用する。**pytest ではAPIを呼ばず**、記録済みの応答か偽のクライアントを使う（例：`tests/test_claude_api.py`）
- APIキーが未設定の場合は、LLMを使う評価を飛ばして進め、完了報告にその旨を書く
- LLMの出力をそのまま数値に使わない。数値を出す場合は、幾何計算による検算を通すこと

## 対象外（今回はやらない）

- 実CADのSTEPの癖（面の分割、微小面）への対応：実データ入手後
- 成形加工（ルーバー、エンボス、バーリング、タップ）、圧入部品、曲げを横切る穴
- 密着ヘム（すき間のない折り返し）：ゴールデンデータは内R 0.5t〜1t のオープンヘムのみ
- 見積ロジック（価格モデル）の改修。ヘムの加工費を別工程として扱う件は別途
